# 0012 機能ブランチ受入れと関連リポジトリ境界

- 日付: 2026-08-10
- 状態: Accepted
- 関連仕様: 開発ガバナンスと進捗管理
- 関連判断: [0001](0001-governance-and-specification-source.md)、[0007](0007-project-scoped-specialist-agents.md)、[0011](0011-roadmap-and-codex-session-lifecycle.md)

## 背景

AirGuardV2は近日中に従業員による試用を予定しており、実装、修正、改修による既存機能の回帰を、利用者確認前に安定ブランチへ混入させない必要がある。また、関連リポジトリはAirGuardV2の基盤を提供するため、調査には広く参照できる一方、変更は全体影響を伴う可能性がある。

## 決定

依頼を機能単位で扱い、原則として `codex/<機能名>` ブランチで実装・検証・コミットする。司令塔が作業者の報告、差分、仕様、テスト、回帰リスクを確認し、受入れた変更だけを機能ブランチへコミットする。

利用者が機能ブランチ上の動作を確認し、明示的に承認するまで `main` へマージしない。`main` への統合は原則として機能単位のマージコミットを作成する。`main` への直接コミット、マージ、Git push、デプロイは別々の承認境界とする。

`air-firebase-v2`、`air-firebase-v2-client-adapter`、`air-firebase-v2-server-adapter`、`air-guard-v2-schemas`、`air-guard-v2-admin-sdk` は、AirGuardV2の調査に必要な範囲で事前承認なく読み取れる。変更する場合は、対象、必要性、利用側、互換性、公開・導入順序、代替案を提示し、利用者の明示的承認を得る。

## 理由

利用者確認前の変更を `main` から隔離し、試用環境の安定性を守りながら、確認後も機能単位で履歴と取消し境界を追跡できるため。関連リポジトリは原因調査に必要だが、変更の波及範囲が大きいため読取りと書込みの境界を分離する。

## 代替案

- 司令塔確認後に `main` へ直接コミットする案: 利用者確認前の変更が安定ブランチへ混入するため標準運用にはしない。
- squashまたはfast-forwardだけで統合する案: 機能単位の統合・取消し境界が弱くなるため標準にはしない。
- 関連リポジトリの読取りにも都度承認を求める案: 調査を不必要に妨げるため採用しない。
- 関連リポジトリを包括的な変更対象とする案: 影響と公開手順を確認せず変更できてしまうため採用しない。

## 影響

- 利用者: 機能ブランチで動作確認し、`main` 統合可否を明示する。
- データ: ブランチだけではデータ変更を隔離できない。実データ、リモート環境、移行は従来どおり別途承認する。
- 実装: 機能単位のブランチとコミットを使用し、統合後に回帰確認を行う。
- 確認: 司令塔の差分・テスト確認と、利用者の実画面・試用確認を分離する。
- 運用: 問題発生時はマージコミットのrevert可否を確認し、安全でなければ修正ブランチと移行・復旧手順を使用する。

## 移行

本ADRを含む今回のガバナンス更新はアプリケーション機能へ影響しないため、利用者の明示承認により例外的に `main` へ直接コミットできる。以後の実装・修正・改修から機能ブランチ運用を適用する。

## 再検討条件

CIによる必須チェック、Pull Request保護、正式なリリースブランチ、従業員試用環境の分離が導入された場合。

# 0011 ロードマップとCodexセッションライフサイクル

- 日付: 2026-08-10
- 状態: Accepted
- 関連仕様: 開発ガバナンスと進捗管理
- 関連判断: [0001](0001-governance-and-specification-source.md)、[0007](0007-project-scoped-specialist-agents.md)

## 背景

AirGuardV2は試験運用を伴う継続開発であり、完了済み機能と正式運用までの残作業を、チャット履歴に依存せず区別する必要がある。また、Codexのハングまたはプロジェクト再作成が発生しても、作業状態、承認境界、未統合差分を失わず安全に再開できる運用が必要になった。

## 決定

`docs/roadmaps/` を目標、残作業、完了条件、証拠に基づく進捗の正本とする。正式運用準備ロードマップは合計100点の加重マイルストーンで管理し、現在はマイルストーン単位の部分加点を行わない。スコープ追加または判定訂正で進捗が低下する場合、変更前、変更後、理由を記録する。

長期のマルチエージェント作業は、タスク間通知を用いたイベント駆動型とする。コーディネーターはレビュー可能なチェックポイントを1件ずつ割り当て、差分と検証を統合してから次へ進む。標準の作業セッション終了条件は「安全に独立実行できる作業が尽きた時点」とする。

コーディネーターのセッション容量が300 MiBに達した場合、新規割当を停止し、基準コミット、進捗、チェックポイント、未統合作業、テスト、承認事項、次の指示をリポジトリへ記録する。コーディネーター交代は利用者の明示承認後に、新しい連番タスクを作成して行い、履歴をforkしない。専門タスクは、安全なチェックポイントで状態と差分が統合済みの場合に限り自動交代できる。

交代前に旧コーディネーターは自身の完了変更を検証・コミットし、専門タスクの変更はコーディネーターが確認・コミット・統合する。やむを得ない未コミット例外は、ファイル、目的、検証、理由、所有者、再開手順を記録し、旧新タスクへ重複所有させない。新タスクのリポジトリ再開、権限設定、コールバック先、最初の実ファイル限定コミットを確認してから旧タスクをアーカイブする。

## 理由

進捗を経過時間や自己申告ではなく再検証可能な成果物で表し、Codexの個別チャットが継続不能になっても、重複作業、未承認変更、未統合差分を避けて復旧できるため。

## 代替案

- チャット履歴だけで進捗と引継ぎを管理する案: ハングや再作成時に再現できないため採用しない。
- 定時ポーリングを標準とする案: 未変更時の不要な確認と割当重複を招くため、コールバック不能時の代替に限定する。
- 閾値到達時にコーディネーターを自動交代する案: 利用者が作業主体の変更を把握できないため採用しない。
- アーカイブを物理削除とみなす案: 保存容量の縮小を保証しないため採用しない。

## 影響

- 利用者: コーディネーター交代と重要な仕様・外部操作は引き続き明示承認する。
- データ: 業務データへの影響はない。チャットや秘密情報をリポジトリへ転記しない。
- 実装: アプリケーションコードへの影響はない。文書、`.codex/`、検証スクリプトを更新する。
- 確認: ロードマップ重み・進捗、文書リンク、TOML、コールバック経路、引継ぎ後のGit操作を確認する。
- 運用: アーカイブ後も容量を再測定し、Codex所有のSQLiteやWALを通常運用で直接保守しない。

## 移行

既存の仕様、ADR、専門エージェント、未コミット差分を保持し、文書案内、ロードマップ、セッション容量確認と引継ぎ手順を追加する。環境変更、データ移行、デプロイはない。

## 再検討条件

Codexのセッション保存方式、タスク間通知、権限設定、アーカイブ動作が変更された場合、または300 MiBより適切な閾値が運用実績から判明した場合。

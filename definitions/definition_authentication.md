## ユーザー管理と認証

### Authentication

- **認証方式**: メールアドレス + パスワード
- **メール認証**: 必須（`sendEmailVerification`）
- **カスタムクレーム**: `{ companyId, isSuperUser }`

### ユーザータイプ

#### 1. 管理者 (Admin)

- 1 つの会社につき 1 アカウントのみ
- `User.isAdmin: true`
- `User.isTemporary: false`
- すべての機能にアクセス可能
- 管理者権限の移譲が可能

#### 2. 利用者 (Normal User)

- 管理者が事前登録したユーザー
- `User.isAdmin: false`
- `User.isTemporary: false`（本登録後）
- `User.roles`配列で権限を管理

#### 3. スーパーユーザー (Super User)

- カスタムクレーム`isSuperUser: true`
- すべての会社のデータにアクセス可能
- Admin SDK で設定（開発者のみ）

### アカウント登録フロー

#### 管理者登録

```
1. 管理者サインアップ画面でメールアドレスを入力
   ↓
2. checkEmailAvailability (Cloud Functions) でメールアドレスの重複確認
   - Usersコレクション全体（コレクショングループクエリ）で確認
   - 他社での利用があっても登録拒否
   ↓
3. 会社情報（会社名、会社名カナ）を入力
   ↓
4. createUserWithEmailAndPassword でAuthenticationアカウント作成
   ↓
5. createAdminAccount (Cloud Functions) を実行
   - Companyドキュメントを作成
   - Userドキュメントを作成 (isAdmin: true, isTemporary: false)
   - カスタムクレーム { companyId, isSuperUser: false } を設定
   ↓
6. トークンをリフレッシュ
   ↓
7. メール認証を送信
   ↓
8. ダッシュボードへリダイレクト
   - ナビゲーションガードでメール認証画面に遷移
```

#### 利用者登録

```
1. 管理者がユーザー管理画面で利用者のメールアドレスを登録、または従業員詳細画面から
   - Userドキュメントを作成 (isAdmin: false, isTemporary: true)
   - この際、User ドキュメントについて同一メールアドレスの既登録（CollectionGroup）がないかを確認。
     - マルチテナントであるため、転職・移籍などによって別会社にアカウントが残っていると同一メールアドレスでのユーザー登録ができない仕様。
   ↓
2. 利用者がサインアップ画面でメールアドレスとパスワードを入力
   ↓
3. checkUserPreRegistration (Cloud Functions) で事前登録確認
   - isTemporary: trueでコレクショングループクエリ
   - 登録されていなければエラー
   ↓
4. checkEmailAvailability でメールアドレスの重複確認
   - 上記1.での重複確認はあくまで `Users` コレクションに対してのもの。ここでは Authentications 内での重複がないかどうかを確認する。
   ↓
5. createUserWithEmailAndPassword でAuthenticationアカウント作成
   ↓
6. setupUserAccount (Cloud Functions) を実行
   - カスタムクレーム { companyId, isSuperUser: false } を設定
   - 仮発行IDのUserドキュメントを削除
   - Authenticationのuidで新しいUserドキュメントを作成
     (isAdmin: false, isTemporary: false)
   ↓
7. トークンをリフレッシュ
   ↓
8. メール認証を送信
   ↓
9. ダッシュボードへリダイレクト
```

### User (ユーザー)

```javascript
{
  docId: string,              // AuthenticationのUID
  email: string,
  displayName: string,
  employeeId: string,         // 従業員IDとの紐付け（未実装）
  roles: string[],            // 権限配列
  disabled: boolean,          // 無効化フラグ
  companyId: string,
  isAdmin: boolean,
  isTemporary: boolean        // 仮登録状態
}
```

**employeeId の用途:**

- 現在未実装
- 将来的に Employee(従業員マスタ)と紐づけて通知機能を実装予定
- すべてのユーザーが従業員であるわけではない（管理者のみのユーザーも存在）

### アカウントの無効化と削除

#### 無効化

- `User.disabled: true`に設定
- `disableUser(uid)` Cloud Functions
- 再度有効化が可能: `enableUser(uid)`

#### 削除

- **管理者**: 削除不可（`User.delete()`でエラー）
- **利用者**: 削除可能
  - User ドキュメント削除時に Authentication 削除も連動
  - `logicalDelete: false`（完全削除）

## 改修目標: 従業員からのユーザーアカウント作成フロー（完了）

### 概要

従業員管理画面から個別にユーザーアカウント（仮登録）を作成できるようにする。

### フロー

```
1. 従業員ドキュメントを作成（通常フロー）
   - email フィールドにメールアドレスを登録
   ↓
2. 従業員管理画面（詳細 or 編集画面）で「ユーザー登録を行う」ボタンを設置
   - Employee.email が登録されていない場合は非表示
   - 既に User ドキュメントが存在する場合は非表示
   ↓
3. ボタンクリック時の処理
   - メールアドレスの登録確認
   - User ドキュメント（全社）で同一メールアドレスの存在チェック
     → 存在する場合: 「既に同一メールアドレスのユーザーが存在します」警告
     → 存在しない場合: User ドキュメント作成
   ↓
4. User ドキュメント作成（isTemporary: true）
   - email: Employee.email
   - displayName: Employee.displayName
   - employeeId: Employee.docId
   - companyId: Employee.companyId
   - isAdmin: false
   - isTemporary: true
   - roles: [] (初期値)
   ↓
5. 従業員に通知（手動 or メール）
   ↓
6. 従業員が sign-up 画面でメールアドレスとパスワードを入力
   ↓
7. 既存の本登録フロー（checkUserPreRegistration → setupUserAccount）
   ↓
8. メール認証完了後、アプリにログイン可能
```

### 実装要件

#### UI改修

**従業員管理画面（詳細 or 編集画面）**

- 「ユーザー登録を行う」ボタン追加
  - 表示条件:
    - `Employee.email` が存在
    - 対応する User ドキュメントが存在しない
  - クリック時:
    1. メールアドレス重複チェック（checkEmailAvailability）
    2. User ドキュメント作成
    3. 成功メッセージ表示

#### 既存機能の活用

- `checkEmailAvailability` (Cloud Functions): メール重複チェック
- `checkUserPreRegistration` (Cloud Functions): 事前登録確認
- `setupUserAccount` (Cloud Functions): 本登録処理
- sign-up 画面: 既存UIをそのまま使用

### 利点

1. **シンプル**: スキーマ変更不要、既存フローを最大限活用
2. **柔軟**: 必要な従業員にだけユーザーアカウントを作成
3. **安全**: メールアドレスの重複を確実にチェック
4. **段階的**: 従業員登録とユーザー登録を分離
5. **UI改修のみ**: Cloud Functions の追加実装が不要

### 注意事項

- 従業員と紐づかないユーザーは引き続き管理者が直接作成
- Employee 削除時の User 処理は別途検討が必要（無効化 or 削除）
- メール重複チェックはコレクショングループクエリで全社チェック

## 今後の検討課題

### 1. 従業員の移籍・転職時のアカウント処理

#### 課題

従業員が別の会社に移籍した場合、同一メールアドレスでのユーザー登録が必要になるケースが考えられる。

**現在の仕様の問題点:**

- メールアドレスの重複チェックはコレクショングループクエリで全社チェック
- 前の会社でアカウントが残っている場合、新しい会社での登録ができない
- 前の会社にアカウント削除を依頼する運用は現実的ではない

#### 検討すべき解決策

1. **Authentication データの companyId 書き換え**
   - カスタムクレームの companyId を新しい会社に変更
   - User ドキュメントも移行または再作成
   - データ整合性の担保が必要

2. **Authentication の強制削除**
   - 管理者権限での強制削除機能
   - onAuthUserDeleted トリガーでクリーンアップ
   - 削除後、新しい会社で再登録

3. **メールアドレス変更フロー**
   - 従業員に新しいメールアドレスでの登録を依頼
   - 古いアカウントは無効化または削除

**決定事項:** 未定（仕様の明確化が必要）

### 2. User ドキュメント削除時の Authentication 削除

**実装状況:** 実装済み

- `functions/modules/Users.js` の `onUserDeleted` トリガーで実装
- User ドキュメント削除時に対応する Authentication ユーザーを削除

### 3. Authentication 削除時のクリーンアップ処理

**実装状況:** 実装済み

- `functions/modules/auth-v2.js` の `onAuthUserDeleted` トリガーで実装
- Authentication ユーザー削除時に FCM トークンを削除
- 将来的に他のクリーンアップ処理を追加可能

### 4. 従業員とユーザーの管理方針（確定仕様）

#### 基本方針

**ユーザーを2種類に分類して管理:**

1. **従業員ベースのユーザー** (`employeeId` あり)
2. **独立ユーザー** (`employeeId` なし)

**注意事項:**

- **独立ユーザーが従業員になった場合:**
  - 管理者メニューから当該ユーザーアカウントを削除
  - 改めて従業員管理機能からユーザーアカウントを作成
  - 理由: データの整合性を保つため（`employeeId` の適切な設定）
  - 注意: Authentication の UID が変わるため、データ引き継ぎは行われない

#### 従業員の退職時の処理

**仕様:**

- 従業員は退職フラグ（`Employee.retired` など）で管理
- 退職処理時にユーザーアカウントは**削除**
  - 理由: 移籍・転籍時に同一メールアドレスでの再登録を可能にするため
- 復帰時は別従業員として再登録（データの整合性を保つ）

**処理フロー:**

```
従業員管理画面で退職処理
  ↓
Employee.retired = true
  ↓
User.delete()（ユーザーアカウントが存在する場合）
  ↓
Authentication 削除（既存トリガー onUserDeleted）
  ↓
FCM トークン削除（onAuthUserDeleted トリガー）
```

**テスト結果:**

1. 従業員から利用者**仮登録**後に**従業員退職処理**で `User` ドキュメントが削除されること。✅
2. 従業員から利用者**仮登録**後に**従業員削除処理**で `User` ドキュメントが削除されること。✅
3. 従業員から利用者**本登録**後に**従業員退職処理**で `User` ドキュメントが削除され、`Authentication` が削除されること。✅
4. 従業員から利用者**本登録**後に**従業員削除処理**で `User` ドキュメントが削除され、`Autnentication` が削除されること。✅

#### 管理者メニュー - ユーザー管理

**機能:**

- **全ユーザーを一覧表示**（`employeeId` あり・なし両方）
- **全ユーザーの `roles` を編集可能**

  - `employeeId` **あり** → 削除不可

**機能:**

  - `roles: []`（権限なし）で作成
